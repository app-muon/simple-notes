# Security and lifecycle decisions

## Boundaries

Tag definitions and note assignments remain inside SQLCipher and encrypted backup manifests. The active tag filter and Find query/ranges are session state cleared on locking; neither is saved in preferences or logs. Find highlights are temporary display styling and never enter persisted documents or undo snapshots. The additive Room 1→2 migration adds tag metadata without changing encryption or enabling a network permission.

The vault protects private application data at rest and gates normal application access using system authentication. It is not a defence against a compromised/rooted OS, an already-authorized external viewer, screenshots the user permits, or keyboard/clipboard behavior controlled by Android and other applications.

The application requests `USE_BIOMETRIC`. AndroidX adds `USE_FINGERPRINT` compatibility declarations and a signature-only internal receiver permission. It does not request `INTERNET`; manifest removal rules also reject transitive Internet declarations. Application components except the launcher/share activity are non-exported. AndroidX also contributes a profile-installation receiver guarded by the system's `DUMP` permission; it has no note-data interface. Providers grant access only to specifically selected URIs. Automatic cloud backup and device transfer are excluded, including device-protected storage domains.

## Key hierarchy

An AES-256-GCM Android Keystore key (`secure-notes-vault-v1`) is authentication-required per operation, accepts strong biometrics/device credentials, and is usable only while the device is unlocked. It encrypts a random 256-bit vault root. The authentication prompt carries the Keystore cipher through a `CryptoObject`; success unwraps the root. New vaults use an authenticated encryption operation to create the envelope. Associated-data updates and finalization both happen after authentication; submitting metadata before authentication also attempts to use the key. No boolean preference bypasses this operation.

Each generation derives separate 256-bit database and file-key wrapping keys using HMAC-SHA256 with distinct generation-qualified labels. SQLCipher protects the Room database, journals, metadata, search sources, and token postings. SQLite temporary storage is in memory and secure deletion is enabled. An AES-GCM envelope protects the generation's random Tink keyset. Attachment ciphertext uses Tink `AES256_GCM_HKDF_1MB` with the attachment UUID as associated data.

Only sort order is stored unencrypted in a generation-local DataStore file. Backup containers never include the local root, Keystore identity, or device-bound keysets.

## Recovery passphrase

On first unlock the app generates an 8-word passphrase from the bundled EFF large wordlist (7,776 words, `SecureRandom`, about 103 bits). It is the second wrap of the same vault root: `<generation>/recovery.key` holds a 32-byte salt followed by AES-GCM(PBKDF2-HMAC-SHA256(passphrase, salt, 600,000), root), with associated data `SecureNotes recovery v1:<generation id>`. The passphrase is also the backup password, so one secret recovers both this phone and backups on a new phone. It is generated, never chosen, so its strength does not depend on the user.

The plaintext passphrase is stored in SQLCipher (`secrets.passphrase`) so Settings can show it again and automatic backups need no prompt. Viewing it requires a fresh BiometricPrompt that completes a vault-key operation, even inside an unlocked session. Screens and dialogs that show or accept the words set `FLAG_SECURE`. A "Copy words" button puts the passphrase on the clipboard for a password manager; the clip is marked `EXTRA_IS_SENSITIVE`, so Android hides it in the clipboard preview and keyboard suggestions, but other apps with clipboard access can still read it until Android clears it. Until the user re-enters three randomly chosen words, the first-run screen blocks the rest of the app.

If the Keystore key is invalidated or missing while `vault.key` or the vault remains (for example after removing the screen lock), the lock screen offers passphrase recovery instead of an error. Recovery unwraps the root from the published generation's `recovery.key`, deletes the unusable device envelope, creates a new Keystore key, and wraps the same root after a fresh authentication. No notes are re-encrypted. A wrong passphrase fails AES-GCM authentication and changes nothing. Passphrase recovery is available only when the device key is unusable; daily unlock remains biometric/device credential.

Anyone holding the passphrase and either this phone's app storage or a backup file can read the notes. That is the intended recovery property. There is no independent phrase-change action; restoring a backup adopts its phrase.

## Automatic backup

The destination is selected with ACTION_OPEN_DOCUMENT_TREE. A versioned configuration record in SQLCipher's existing secrets table records disabled, legacy, or pair state. A pair contains the folder grant, actual provider-returned filenames and URIs, ciphertext lengths and SHA-256 digests, active slot, normalized phrase hash, content fingerprint, last verified time, pending work, and structured error. The complete record is committed atomically. It is excluded from exported contents and hidden from status observers while locked. No Room schema change is needed.

A coordinator mutex serializes save, setup, disable, and restore publication. The scheduler separately owns the 60-second debounce, one-second metadata refresh, lifecycle triggers, and short foreground-service holds. Later changes never cancel a ciphertext write. Semantic repository revisions exclude indexing progress and backup settings. Metadata is read in a short transaction; the repository mutex prevents attachment deletion while encryption streams outside that transaction. The fingerprint canonicalizes metadata, preserves explicit manual order, and includes the normalized phrase hash. Both reader and writer enforce the unchanged 16 MiB manifest limit; total backup size remains unlimited.

Before any inactive-slot write, the coordinator validates configuration, phrase, persisted read/write grant, and the active file's exact length and digest. A mismatch pauses backups until a new pair is created; a read/access failure leaves the inactive file untouched. Pending work is committed before writing. The ciphertext write and read-back verification are non-cancellable; final active-slot evidence is published only after verification and an acknowledged settings commit. If the session closes before final recording begins, the durable pending record and previous active slot remain, and unlock retries. Any failed or uncertain settings write after it begins blocks backup mutations for the rest of the process, including after lock/unlock and restore. Authentication cancellation before a write starts is not a settings failure.

Changed or forced saves also verify the active file before encryption and key derivation. This adds one sequential read on a successful save, but unreadable or damaged active files fail without preparing new ciphertext on every retry. The full verification immediately before the inactive write remains mandatory because provider content can change during preparation. Unchanged automatic saves still skip file reads.

Document opening falls back from rwt to wt to w only when opening fails; security failures anywhere in a cycle-safe cause chain propagate immediately. Every successful open is followed by streaming copy, explicit flush, explicit truncation for plain w, fsync, close, and streamed verification with bounded buffers, exact EOF, and SHA-256. EINVAL, ENOTSUP and ESPIPE from fsync are accepted for providers with descriptors that do not support synchronization; other errors fail. This is local provider verification, not proof of external upload or hardware power-loss durability. See [Android's provider mode contract](https://developer.android.com/reference/android/content/ContentResolver#openFileDescriptor(android.net.Uri,%20java.lang.String)) and [Os.fsync](https://developer.android.com/reference/android/system/Os#fsync(java.io.FileDescriptor)).

Setup prepares one ciphertext artifact and creates two new timestamped documents, initially publishing B as active only after both verify. It stores actual returned names, rejects duplicate or already managed URIs, and never adopts documents by name. Pre-commit failure/cancellation removes only this attempt's documents and unused grant. An uncertain commit retains both pairs and grants. Success releases the previous grant only after committing; historical files stay intact. Disable commits first, then releases the grant, leaving files. Upgraded legacy files are read-only history until the user selects a folder for migration.

An in-memory scheduler reservation covers folder selection, provider acknowledgement, queued setup and its first flush. It holds neither the coordinator mutex nor a service during selection. Automatic triggers coalesce and fingerprint refreshes defer. Setup arriving before resume waits; foreground return acquires its service hold synchronously before flushing. Jobs register ownership and completion cleanup before execution. Lock invalidates selection identities and cancels preparation; stale callbacks must select again. Restore publication still serializes through the coordinator and setup reads the latest configuration.

Accepting either a local folder or an acknowledged provider transfers setup ownership from the view model to the process-wide scheduler, including results queued before resume. Clearing the view model cancels only unsubmitted selection. An accepted setup continues after activity destruction, subject to the existing lock cancellation and service timeout. When an automatic or manual save has deferred work on completion, its same job keeps its service hold through grant refresh, edit flush and the follow-up attempt, even while the activity is invisible. The flush still runs if the first attempt made further backup writes ineligible.

Created URIs are validated and recorded before metadata queries. Missing, blank or ordinarily unreadable display names use the requested label with `nameConfirmed=false`; Settings explicitly marks that label unconfirmed. Security failures and cancellation propagate after recording the URI for cleanup. Old configuration slots default to `nameConfirmed=true`. URIs remain the sole file identity.

Restore staging contains no destination snapshot. Publication obtains the latest device configuration under the coordinator mutex, preserves active evidence, and marks pending work. The phrase that decrypts the restored backup becomes the recovery phrase. A different phrase pauses the old pair until fresh authentication, phrase review, and creation of a new pair; the old files keep their original phrase. Established missing phrases block setup instead of triggering generation. First-run generation and confirmation are retained.

Automatic saves skip collections with no notes and no tag definitions. Manual saves and explicit setup may save empty content. Pending work and retryable failures override unchanged-fingerprint skipping. Lost grants wait for an IO refresh of cached permission state; synchronous eligibility and composition perform no provider calls. Storage operations recheck actual access on IO inside their error boundary. A refresh completing after backgrounding cannot start new work without an existing hold. Oversized manifests wait for a newer revision in this process only: lock/unlock retains suppression, while process restart allows one fresh check. Old persisted error revisions still decode but are ignored; new errors omit them. Successful setup, disable and restore publication clear suppression. Phrase changes and damaged active evidence require action. Diagnostics include at most five exception class names and errno names, never exception messages or private paths.

An active-file read failure reports that its condition could not be verified and that no backup file was overwritten. It stays retryable and offers a new pair if missing. Digest/length mismatch remains proven changed evidence requiring a new pair. Inactive-write errors state only that the active file was not overwritten by this attempt. Setup errors remain separate from current-backup errors and direct users back to folder selection.

For access failures with unknown or missing cached permission, Settings offers an enabled **Check backup access** action. It refreshes permission eligibility on IO without encrypting, writing or taking a service hold; when access is confirmed, the action becomes **Back up now**. The storage attempt still checks actual access and may report a per-document denial even when the folder grant exists.

The service notification is minimal and silent; holds release on job completion, including cancellation before execution. Service timeout remains Android's short-service limit. Both files should be synced in upload-only mode from a dedicated phone-storage folder. Providers with delayed/stale reads can fail local verification; the UI warns before selecting other providers.

Startup idempotently removes only the obsolete `backup` notification channel, preserving `verified-backup` and its settings. The internal `@VisibleForTesting` backup creation helper deliberately bypasses phrase confirmation for fixtures; production preparation always requires confirmation.

### Intentional format and privacy decisions

The A/B protocol retains streamed .ssnb/Tink encryption with fresh salts and keys, attachment streaming, and staged vault publication. It does not introduce whole-file JSON encryption, a total-size cap, cached derived keys, plaintext preferences, or plaintext JSON export. Explicit content revisions are retained instead of Room invalidation. Existing backups remain readable. The unchanged envelope cannot always distinguish incorrect phrases from damaged or truncated files before full decryption.

## Session lifetime

The authorization state exists only in process memory. The session is closed at device lock; a new process always requires authentication. Activity recreation and ordinary backgrounding alone do not close it. `KeyguardManager` is checked on resume and before sensitive I/O, with runtime screen/unlock receivers invalidating sessions after screen cycles. Android does not give ordinary apps an unrestricted, reliable history of every keyguard transition. If a screen-off cycle cannot be proven safe, resume conservatively requests authentication. This can also happen if the display turns off during a device lock grace period. No inactivity timer or privileged listener permission is used.

Lock immediately removes sensitive Compose/model state, revokes ordinary repository access and outgoing grants, freezes new edits, and cancels other work. A private close operation finishes writing only the snapshots already accepted before the lock; then it closes the vault and clears keys. It cannot import files or grant read access while locked. Concurrent unlocks are serialized, opening an existing vault is idempotent, and a lock invalidates an unlock still in progress. The VM/OS/libraries can retain inaccessible managed-memory copies until garbage collection; zeroization is best effort. Delayed/missed OS scheduling is not represented as an instantaneous hardware memory wipe.

Recents task snapshots are disabled (`setRecentsScreenshotEnabled(false)`), so note content is not captured into system-managed snapshot storage or shown in the app switcher after locking. User-initiated screenshots remain possible.

Both native body editors and Compose title/search/password fields request `IME_FLAG_NO_PERSONALIZED_LEARNING`. This requests cooperation from the selected keyboard; it cannot enforce a third-party keyboard's behavior.

## Attachment access and temporary data

External opening uses a non-exported, grant-enabled content provider. A seekable proxy descriptor decrypts Tink segments on demand. Its callbacks check the live session and per-launch grant, so revoking a grant also prevents subsequent proxy reads through already-open descriptors. Previously read bytes cannot be recalled. No plaintext export file is created for an external viewer or PDF indexing.

Sharing uses the same provider under a separate `shared/<id>` path. Android revokes a URI together with its sub-paths, and the two paths do not nest, so revoking viewer grants on return leaves share grants in place. Share grants end with every other grant when the device locks, and every read also requires the live session. Notes excludes itself from its share sheet. No plaintext file is written for sharing.

Save to device is the one deliberate plaintext export. It streams the decrypted attachment to the document the user picked, checking the session for every chunk, while the repository mutex keeps the blob from collection. A failed or cancelled save deletes the partial document, including a save cancelled or locked out while it waits behind indexing, a backup or another operation. A picker result that arrives after locking, or after process death, is not written. The picker's document is deleted only if the provider reports its size as exactly zero, so a chosen existing file, or one of unknown size, is kept. Android lets a provider ignore truncation for `"w"`, so Save uses `"wt"`, and falls back to `"w"` only for a document known to be empty; replacing an existing file on a provider without `"wt"` fails instead of leaving its old trailing bytes. Shared and saved files are the original bytes, including EXIF metadata such as GPS location.

Camera capture needs a writable file for third-party compatibility. A narrowly scoped FileProvider exposes only the camera cache directory. The pending destination and stable import IDs are saved in SQLCipher before launching the camera. Its activity-result callback remains registered while the vault is locked; only a non-sensitive success/cancel flag is stored outside the vault. Pending capture files survive recreation/restart until imported or explicitly discarded. Orphan captures are cleaned after authentication. An interrupted capture without a definite result prompts the user to keep or discard it. Images decode through seekable encrypted descriptors with EXIF orientation and bounded output dimensions. Captures are named after the capture file's modification time, which the camera sets when it writes the shot. Original URI import permissions are released after import when persistable grants were obtained.

File import is staged to an encrypted `.part`, synced, then renamed before metadata/document publication. Import jobs are recorded in the encrypted database. On restart, partial/orphan files are removed and surviving jobs retry from their source URI. Persistable URI grants are retained while an interrupted job remains pending. Source permission loss is reported without destroying other data. Index progress is stored per attachment (PDF page or plain-text character offset); chunks finish complete words. Parsing failures fall back to filename search. PDF parsing uses Android's maintained native parser in the app process; keep Android security updates installed.

## Persistence and replacement

The repository retains only the latest immutable snapshot per note. Autosave waits for 300 ms of quiet, with a maximum scheduling delay of one second during continuous typing (disk completion can take longer). Navigation/backgrounding flush pending changes. Saving reindexes changed sources only and updates the affected note in memory. Failed saves remain pending; failures are reported instead of silently discarded.

If a final lock-time database write fails, the remaining snapshots are authenticated-encrypted under a generation-specific key and saved as `pending.edits` for replay after authentication. If even that write fails, only encrypted recovery bytes remain in process memory, with a warning that closing the process may lose those edits. No software can promise persistence when all storage writes fail. Recovery records are removed after successful replay. They are temporary crash recovery, not persistent undo history.

Search enumerates distinct matching terms in ordered pages, keeping prefix/exact matching separate from fuzzy vocabulary matching. Matching postings are also paged, so a large document cannot crowd other notes out of an arbitrary candidate limit.

All current data belongs to a UUID generation under app-private `noBackupFilesDir`. Restore checks the bounded container header before asking for a password. This is structural validation only; it is repeated when decrypting, and authenticity is established only by full authenticated decryption. A key-envelope authentication failure is reported as an incorrect password or damaged file, without pretending to distinguish them. Restore prepares a separate encrypted generation, validates references/checksums and the version, and waits for explicit confirmation. Publishing an AtomicFile generation pointer is the commit point. Startup selects the published generation and removes abandoned generations. The previous generation exists only to make replacement recoverable until commit, not as user-accessible history.

Settings, the recovery passphrase, and the generation's `recovery.key` are included in the replacement transaction's generation. A restore adopts the phrase that successfully decrypted the backup, whether it came from confirmed device storage or phrase entry. Android/flash/filesystem durability ultimately constrains power-loss guarantees; ordinary process interruption is covered by staging, database transactions, and atomic publication. No automatic deletion is performed when the current database or key cannot be opened.

## Review rules

Never add note contents, filenames, passwords, or keys to logs, exceptions shown verbatim to users, saved-state bundles, analytics, or crash reporters. Do not add a release authentication bypass. Preserve the no-network manifest check, ciphertext inspection tests, and malformed/truncated backup tests when changing storage or dependencies. Future migrations must not use `fallbackToDestructiveMigration`.
